# Переход на раздельное имя клиента

На новой БД Flyway применяет всю цепочку V1–V4. Для обновления работающего
приложения миграции запускаются поэтапно:

1. На версии после ЛР2 применить V3 (`SPRING_FLYWAY_TARGET=3`).
   Старая колонка остаётся, существующие имена заполняют новые колонки.
   Триггер синхронизирует записи старого и нового приложения в обе стороны.
2. Развернуть версию после ЛР3 с `SPRING_FLYWAY_TARGET=3`.
   Она читает и пишет только first_name/last_name; триггер сохраняет full_name
   для ещё работающих старых экземпляров. Проверить чтение и создание заказов.
3. Дождаться завершения всех старых экземпляров и их транзакций.
   Затем применить V4 (снять ограничение target). Она уберёт триггер и full_name.
   Новая версия продолжает работать с теми же полями.

До V4 можно вернуться на приложение ЛР2, пока сохранена full_name.
После V4 откат к старому бинарнику требует отдельной обратной миграции.
DDL берёт кратковременные блокировки: на большой рабочей таблице backfill
нужно выполнять небольшими порциями, а построение индексов — отдельно.

Имя разделяется по первому пробелу; остаток сохраняется целиком.
Для одного слова last_name — пустая строка. API продолжает возвращать
customerFullName в прежнем формате.

Проверки: эталонный LoadDuringMigrationReferenceTest читает старую колонку
при expand. Собственный MigrationApiLoadTest проверяет HTTP-чтение и запись
новой версией при contract. MigrationDataTest проверяет данные и dual write.
